# v1.0 → v1.1 migration roadmap

Date: 2026-07-04
Author: gambuu (AIWORK builder)
For: Gabriel (AIWORK operator)

## Context

v1.0 ships with **H1 (1-hour) XAU/USD bars** spanning 2024-07 to 2026-07,
from the merged archive at `data/xauusd/xauusd_h1_merged.parquet`. The rubric
spec originally called for **M5 (5-minute) bars for 2024 only**, sourced
from Dukascopy. Three reasons we shipped with H1 instead:

1. `download_xauusd.py` (in `verifier/workspace/`) was the spec's intended
   pipeline but produced H1 files when run on 2026-07-03 (output: 300 KB,
   expected ~150 MB). The M5 step was likely truncated by network or time.
2. The H1 data is real, clean, 24 months deep, and already on disk — no
   additional risk.
3. H1 gives a longer test window per case (60 H1 bars = 2.5 days of context
   vs the spec's 100 M5 bars = 8 hours), which makes the audit harder to
   game via memorization.

Gabriel approved this as **Option A** on 2026-07-04.

## What v1.1 should do

The M5 swap is a clean v1.1 milestone. Items:

### 1. Regenerate M5 data from Dukascopy (or alternative)

- Run `download_xauusd.py` again with a working network path to
  `https://www.dukascopy.com/client/historical/data/xauusd/...`
- The script targets `YEAR = 2024` (single year). Extend it for 2025 + 2026
  if we want the same 24-month coverage on M5.
- Alternative source if Dukascopy is rate-limited: HistData.com, TrueFX, or
  any source covering XAU/USD M5 for the same period.
- Output: parquet at `data/xauusd/xauusd_m5_2024_2026.parquet` (or similar).
  Same merge + TZ-normalize pattern as the H1 archive.

### 2. Recalibrate the rubric bar counts

The rubric's `bar_count_per_case` and `forward_horizon_bars` are
timeframe-specific. Move back to M5-calibrated values:

```yaml
bar_count_per_case: 100   # 100 M5 bars = ~8 hours (was 60 for H1)
forward_horizon_bars: 12  # 12 M5 bars = 1 hour (was 12 for H1; same number
                          # of bars but different wall-clock duration)
```

Other rubric fields (4 scoring dimensions, weights, grade bands,
distribution, thresholds) are timeframe-agnostic and stay the same.

### 3. Run a comparison audit (H1 vs M5)

Goal: confirm the v1.0 mavisgold cert signal is stable across the timeframe
swap. If mavisgold scores A+ on H1 and FAIL on M5 (or vice versa), the
rubric has a timeframe-sensitivity problem we should surface explicitly.

- Same seed, same agent endpoint, two runs (H1 and M5).
- Compare dimension scores, per-regime scores, and overall grade.
- If grades diverge by more than one band (e.g., A on H1, FAIL on M5),
  flag for rubric authors and consider whether H1 and M5 should produce
  separate certs (e.g., `trading_signals_xauusd_h1` vs `..._m5`).

### 4. Update the seed_source string

After the swap:
```yaml
seed_source: "public_archive_dukascopy_xauusd_m5_2024_2026_merged"
```

Remove the Option-A "yahoo_finance" naming — that was Gabriel's example
for H1 only.

### 5. Re-publish the rubric

- Status flips from `published` to `superseded` for v1.0
- v1.1 ships at `rubrics/trading_signals_xauusd/v1.1.yaml`
- v1.0 certs (issued under H1) remain valid until expiry (90 days)
- v1.0 re-audits require M5 cert instead

### 6. Update audit endpoint spec

The mavisgold audit endpoint must accept M5 bars (60 M5 bars instead of
60 H1 bars per case). Spec change:

```json
{
  "case_index": 0,
  "bars": [/* 60 M5 bars, 5-min apart */],
  "decision_bar": {/* last bar */},
  "rubric_id": "trading_signals_xauusd",
  "rubric_version": "1.1",
  "latency_budget_ms": 5000
}
```

The agent needs to handle 8 hours of M5 context (vs 2.5 days of H1 context
in v1.0). Different agent prompts may be needed.

## Items NOT in v1.1 (deferred to v1.2+)

- Adversarial red-team tier (the "is the agent gaming the test" check)
- Multi-skill certifications
- Continuous attestation primitive
- Per-buyer filtering ("show me agents > 80 in ranging regime")
- Cost / payment model
- Per-agent historical cert timeline
- Auto-renewal of expiring certs

These are listed in `/spec` Section 12 ("What this spec does NOT cover").

## Test for "v1.1 is done"

When ALL of these are true:

1. M5 data regenerated, merged, TZ-normalized, served at the canonical URL
2. Rubric YAML updated to M5 bar counts, status `published`
3. Comparison audit run on mavisgold, results documented in
   `/docs/v1.0-vs-v1.1-comparison.md`
4. If grades diverge by more than one band: rubric gets a
   `timeframe-sensitivity` note in the YAML header explaining why H1 vs M5
   differ
5. Homepage stat counter still increments correctly (no schema change)
6. Test set generator reproducibly produces byte-identical cases from the
   same seed (same reproducibility criterion as v1.0)
